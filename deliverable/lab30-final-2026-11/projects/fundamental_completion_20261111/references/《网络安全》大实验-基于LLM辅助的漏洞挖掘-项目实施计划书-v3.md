# 第 1 章　实验概述

## 1.1　实验目的与背景

### 1.1.1　实验背景

近年来，大型语言模型（LLM，Large Language Model）在代码理解与生成上展现出显著能力，安全研究者开始探索将其引入源代码安全审计。传统静态分析工具（如扫描器、污点分析）依赖人工编写的规则与数据流引擎，存在规则覆盖不全、跨文件/跨语言追踪困难、误报率高、无法理解业务语义等问题；而纯人工审计则成本高、依赖个人经验、难以规模化。

本实验的目标，是把 LLM 的代码理解能力与**自动化漏洞挖掘流程**结合，构建一条"**代码预处理 → Prompt 提示词工程 → LLM 推理挖掘 → POC 验证实操 → 结果校验降噪**"的完整链路，并在**Lab30 可控靶场**上验证检出、定位、POC 与复核能力，分析其与传统工具结合时的收益、代价及适用边界。实验结论限定于所测数据、模型和预算，不外推为对未知真实项目的普遍能力。

### 1.1.2　工程载体：VULN-AUDIT 平台

为支撑本实验，团队自主设计并实现了 **VULN-AUDIT 源码白盒审计平台**。该平台是一个"以漏洞发现为目标"的源码审计系统：导入源码 ZIP → 从已有快照发起审计 → 定义审计目标 → 主 Planner 借助项目图与全量只读工具理解项目 → 建立项目级任务图 → 多 Worker 并行审计 → 导出漏洞候选与可复核证据 → 可选在隔离容器中自动执行 POC 验证。

平台不是"套一个 LLM 调用框架"，而是把**实验链路各环节工程化**：

- **代码预处理**：快照冻结 + tree-sitter 语法索引（PHP）+ 纯文本行索引（其他语言），形成 LLM 可读、可证据回溯的标准化源码输入；
- **Prompt 工程**：内置多版本 Worker 审计策略（W0-v1 / W1-v2 / W2-v2）、四段式结构、防幻觉约束、输出格式强制约束，并支持协议化横向对比实验；
- **推理挖掘**：三级分层推理（语法 → 语义 → 业务风险），Planner 动态维护跨文件任务图，Worker 原子领取任务、读源码、产出结构化结论；
- **POC 验证**：隔离 poc-runner 容器中登录本地 Lab30 靶场执行 POC，收集正常/攻击两侧观测证据，并由 Planner 复核；
- **结果校验**：源码边界校验 + POC 验证 + Planner 复核 + CVSS 3.1 定级 + 防御可信度评分，形成多道防幻觉防线。

### 1.1.3　实验意义

1. **贴合企业安全运维真实工作链路**：LLM 辅助人工漏洞挖掘，自动生成漏洞分析报告与 POC 验证脚本，人工复核验证真伪，统计误报漏报并优化——这正是当前安全团队引入 AI 的真实模式；
2. **检验 LLM 的实际能力边界**：通过自建靶场真值集、重复实验与对抗样本，量化 LLM 在精确定位、防注入、证据链完整性等方面的真实表现，而非理论空谈；
3. **沉淀可复用的流程与方法论**：本实验产出的 Prompt 模板、切片规则、校验降噪规则、联动方案，均可迁移到后续的代码安全工作中。

# 第 2 章　传统漏洞挖掘与 LLM 辅助漏洞挖掘技术对比

## 2.1　传统漏洞挖掘技术概览

### 2.1.1　静态分析（SAST）

静态应用安全测试（Static Application Security Testing，SAST）在不运行程序的情况下分析源码，代表性手段包括：

- **基于规则的扫描器**：如 Checkmarx、SonarQube、以及开源的正则/模式匹配工具，通过预定义漏洞模式匹配源码；
- **数据流/污点分析**：跟踪"污点源（输入）→ 传播路径 → 敏感操作（Sink）"，典型代表如 Semgrep、CodeQL、grep（简化的 taint 引擎）；
- **代码属性图与跨函数分析**：CodeQL 通过构建 AST、数据流图与调用图进行跨函数查询。

**优势**：可自动化、可规模化、覆盖全量代码、结果可复现。

**局限**：
1. **规则覆盖不全**：对新型、业务定制型漏洞（逻辑越权、二次注入）规则难以穷尽；
2. **误报率高**：不理解业务语义，易把"防护到位"的代码判为漏洞；
3. **跨语言/跨文件追踪困难**：多数工具绑定单一语言，跨文件动态加载、框架路由难建模；
4. **无业务上下文**：难以区分"真实可利用"与"理论上存在"。

### 2.1.2　动态分析（DAST / IAST）

动态应用安全测试（DAST）通过向运行中的应用发送请求观测响应，代表如 Burp Suite、AWVS、OWASP ZAP。交互式测试（IAST）则结合运行插桩。优势是能观测真实执行；局限是依赖可运行环境、覆盖面受入口与状态影响、对需要特定业务前置条件的漏洞（如特定登录态）覆盖不足。

### 2.1.3　人工审计

资深审计人员结合经验、上下文与工具手工追踪数据流。质量高、能理解业务语义，但**成本高、依赖经验、难以规模化**，且跨大代码库时人易遗漏。

## 2.2　LLM 辅助漏洞挖掘的能力与机制

LLM 辅助挖掘把"语言模型对代码语义的理解"接入上述流程：

1. **语义理解**：LLM 能结合函数名、注释、业务上下文理解代码意图，判断某处是否构成可利用漏洞，降低规则式误报；
2. **推理与定位**：给定目标与代码窗口，LLM 可推理出数据流的输入 → 传播 → 危险操作，并定位到具体文件与行号；
3. **自动生成 POC**：可让 LLM 直接输出针对特定漏洞、可运行的验证脚本；
4. **多智能体协作**：Planner 负责全局任务规划与态势感知，Worker 负责具体区域审计，模拟专家分工；
5. **可对话式追问**：与静态工具不同，可针对某个方向反复追问、交换上下文。

## 2.3　逐维度对比

| 对比维度 | 传统静态扫描器 | 人工审计 | LLM 辅助审计（本平台） |
| --- | --- | --- | --- |
| 语义理解 | 弱（规则/数据流） | 强 | 强（语言模型语义理解） |
| 覆盖全量代码 | 好 | 差 | 好（快照全量索引 + 任务图派发） |
| 跨文件追踪 | 中（绑定语言） | 中 | 中-强（项目图 + 跨文件窗口；Lab30 实测跨文件污点链仍为盲区，见 11.1 节） |
| 误报控制 | 差（规则盲匹配） | 好 | 好（源码边界校验 + 复核；定稿 P 0.9565） |
| 业务逻辑漏洞 | 弱 | 强 | 中（依赖上下文注入；CSRF/越权类仍有漏报，见 7.3 节） |
| 可复现性 | 好 | 差 | 好（冻结快照/目标/预算/项目图 + 离线重算脚本） |
| 自动 POC 生成 | 无 | 人工 | 有（隔离容器自动验证，定稿 47 jobs / 24 confirmed） |
| 成本与规模 | 低 | 高 | 中（模型调用成本 + 预算控制） |
| 定级一致性 | 无（仅告警） | 依赖经验 | 中（CVSS 确定性计算，但指标准确率待提升，见 7.3.3） |

**关键结论**：LLM 辅助挖掘不是取代传统工具，而是**语义理解能力 + 自动化流程**的结合，重点解决"规则覆盖不全、业务语义缺失、POC 生成自动化"三大痛点；其短板（幻觉、不可信输出、成本、跨文件盲区、业务语义盲区）由本平台的多道校验防线与第 10 章专项计划弥补。

## 2.4　本平台与传统工具/人工结合的定位

在后续加分项（第 10.2 节）中，本计划书还将设计 LLM 辅助挖掘与 **Burp/AWVS 传统扫描工具**的联动方案：用传统工具快速圈定候选入口与低垂果实，用 LLM 做深度业务语义分析、二次注入与逻辑漏洞挖掘、以及 POC 生成，形成"粗扫 + 精析 + 验证"的互补闭环。

## 4.2　代码清洗规则

### 4.2.1　清洗原则

清洗目的是**去噪而非删证据**：只剔除对 LLM 判断无帮助且占上下文的信息，保留与漏洞判定相关的原始行号、语义与关键代码。所有清洗基于不可变快照，可追溯、可恢复。

### 4.2.2　逐条清洗规则

| 编号 | 清洗规则 | 作用 |
| --- | --- | --- |
| R1 | 剔除无信息量注释（如"// TODO 优化"、自动生成头注释） | 减少冗余 token，避免干扰语义判断 |
| R2 | 合并多余空行与缩进噪声 | 压缩上下文，聚焦有效代码 |
| R3 | 移除无关业务代码片段（与本漏洞方向无关的模块） | 避免把 LLM 注意力引向无关区域 |
| R4 | 剔除二进制文件内容（只登记大小） | 快照安全 + 避免无效输入 |
| R5 | 归一化换行符与空白 | 统一格式，稳定切片与行号 |
| R6 | 标记并跳过超出容量预算的单条目 | 明确 skipped_files，避免静默丢失 |
| R7 | 保留完整原始字节与哈希 | 证据可追溯、防篡改 |

### 4.2.3　清洗与证据的平衡

清洗**不改变**已读源码行号与原文：Worker 读到的就是快照原始源码行。清洗主要作用于"切片给 LLM 的窗口内容"与"索引建库"，而非改动证据本身。

### 4.2.4　清洗效果量化

C 的 D-C03 已有 Lab30 文件级统计：归档 56 个文件、实际处理 PHP 52 个，原始/清洗后均 343 行、13,516 tokens，缩减率 0%。该样本无可去除冗余，零收益可如实报告，不以强制删减制造效果。

此处 tokens 使用 `cl100k_base` 作为统一估算口径，不等于 DeepSeek 实际计费 tokens。需交接 `analyze_dc03_v2.py`、样本 ZIP、依赖版本与完整命令；以 D-C03 JSON 为机读来源。phpMyFAQ 的大规模预处理结果可选作附录，不要求新增比较实验。

## 4.3　代码切片设计

### 4.3.1　切片需求

LLM 上下文窗口有限，长文件无法整体送入。需设计稳定、可重叠、保语义的切片策略。

### 4.3.2　切片策略（平台实现）

| 项 | 设计 |
| --- | --- |
| 切片最大长度 | 依据模型上下文与预算设置，默认在单次请求/阶段预算约束内控制 |
| 拆分依据 | 按语法边界（tree-sitter 语法索引）优先，其次按函数/类/模块边界 |
| 重叠规则 | 相邻切片设置重叠窗口，保证跨切片函数调用、数据流上下文不丢失 |
| 稳定窗口 | 以 tree-sitter 语法结构定位稳定源码窗口，避免按纯字节切碎函数 |
| 行号保留 | 每个切片内保留原始文件行号，作为证据引用锚点 |

### 4.3.3　跨文件上下文

单文件切片不足以覆盖跨文件漏洞（如二次注入、路由 → 处理函数）。平台通过**项目级任务图**把相关文件组织成可交接的依赖任务，Worker 可检索其他 Worker 的受限工具轨迹作为线索，但引用证据仍须自行读源码行。

### 4.3.4　切片分布量化

C 的 Lab30 样本已有 72 个切片，行数均值 4.7、最大 36；token 均值 187.6、最大 1323，无重叠切片，均为 unit_end 边界。可复用已交 Lab30 双分布直方图，图中约 5 行/188 tokens 为四舍五入值。切片 token 合计 13,508 与整文件 13,516 的微差来自 BPE 边界，二者分别标注。补齐脚本/归档后即可复算。

## 4.4　输入标准化设计

### 4.4.1　标准输入模板

给到 LLM 的标准输入统一为（示例结构）：

```text
【审计目标】<目标描述>
【验收条件】在所选源码中找到至少一处由原始行号证据支撑、具有明确风险等级和触发条件的目标相关漏洞风险
【项目结构概览】<模块/静态include图/高置信入口/未解析关系统计>
【当前任务】<前沿任务描述与依赖摘要>
【源码窗口】<文件路径 + 起始-结束行号 + 代码原文>
【上下文】<本轮态势：前沿与已结算方向、已有结论、覆盖统计>
```

### 4.4.2　统一格式规范

- 代码统一为 UTF-8，行号前置，缩进保留；
- 路径用标准相对路径，禁止绝对路径泄露；
- 验收条件与目标随任务冻结，不可在运行中修改；
- 内置提示词受保护，自定义草稿可编辑/派生。

## 4.5　模块输出定义

模块一最终交付给 LLM 的标准化成果包括：

1. **不可变快照**：ZIP 哈希、文件清单、tree-sitter 语法索引、纯文本行索引、warnings/skipped；
2. **项目结构概览**：模块划分、静态 include 图、高置信入口、引导文件、未解析关系统计；
3. **标准化任务输入**：目标 + 验收条件 + 预算 + 项目图 + 源码窗口 + 本轮态势；
4. **侦察简报**：布局、入口候选、数据存储、安全边界、首批阅读目标（导航线索，非证据）。

# 第 5 章　模块二：Prompt 提示词工程设计（核心得分点）

> **模块核心目标**：通过精准提示词，让 LLM 实现漏洞定位分析 + 自动生成可运行 POC 脚本。

## 5.1　标准化 Prompt 四段式结构设计

平台统一采用四段式 Prompt 结构，作为所有 Worker 审计策略的骨架：

### 5.1.1　四段式结构

```text
第一段：安全审计角色定义
  "你是资深白盒安全审计专家，基于给定源码行号进行审计……"

第二段：漏洞挖掘核心任务
  "追踪上传入口到文件写入操作，确认是否存在未经路径规范化的可达写入路径……"

第三段：漏洞判定标准
  "仅当存在可验证的输入→传播→危险操作证据链且可被利用时才判为漏洞；
   源码行为、防护有效、不构成漏洞记为排查记录……"

第四段：输出格式强制约束
  "输出必须包含：漏洞类型、文件路径与行号、输入来源、传播路径、
   危险操作、影响、利用前提、CVSS 向量、POC 使用说明……"
```

### 5.1.2　设计依据

- **角色定义**限定输出风格与专业口径，避免泛化回答；
- **核心任务**将模糊目标翻译为可执行、可验证的具体任务；
- **判定标准**把"是不是漏洞"固化为可复检的统一标准，压降误报；
- **输出约束**强制结构化，保证结果可解析、可证据回溯、可进入校验链。

## 5.2　分漏洞场景定制 Prompt

### 5.2.1　设计原则

每类漏洞的专属 Prompt 必须包含：**专属判定规则 + LLM 输出可直接运行的 POC 验证脚本**。平台内置多版本 Worker 策略（W0-v1 基础审计 / W1-v2 定位与防护取证 / W2-v2 跨文件与业务取证），并支持提示词库版本派生。

### 5.2.2　分场景清单

| 漏洞场景 | 专属判定规则要点 | POC 输出要求 |
| --- | --- | --- |
| SQL 注入 | 输入 → 拼接进 SQL 语句 → 无参数化/转义；给出可控参数与注入点行号 | 可运行脚本，正常/攻击两段对照，唯一标记判别 |
| 反射型 XSS | 输入 → 未过滤回显到响应；判定需浏览器执行证据 | 响应体含 payload 不足以证明，需渲染侧证据 |
| 命令注入 | 输入流入 shell 命令拼接；给出命令拼接点与可控输入 | 唯一标记 + 正常/攻击两段对照 + 退出码结论 |
| 越权/逻辑漏洞 | 未认证可访问的管理路由、资源属主校验缺失、业务状态错误 | 需登录态/资源属主前提，分步验证 |

E 文稿已有 S-secondorder、S-authz、S-state 三类 Lab30 专属 Prompt；本版 P9 改为将三份全文、版本及注册/调用导出归档，记录输入业务上下文和输出契约，不再要求真实仓库新增场景。

## 5.3　防 LLM 幻觉约束设计

### 5.3.1　约束规则

1. **强制行号**：结论必须标注实际读过的源码文件路径与行号，未读行不得引用为证据；
2. **禁止泛化**：禁止给出无证据支撑的"疑似漏洞"；静态导航不算证据；
3. **限定适用场景**：说明漏洞的利用前提（登录态、资源属主、CSRF、业务状态、必要配置）；
4. **POC 使用说明**：POC 必须附带输入、预期判别与运行说明；
5. **两段对照**：POC 采用正常输入/攻击输入两段观测对照，杜绝"HTTP 200 即漏洞"的粗糙结论。

### 5.3.2　平台的防幻觉防线（系统性机制）

平台不依赖单一 Prompt，而是叠加多道工程防线：

| 防线 | 机制 |
| --- | --- |
| 受限解释器 | 模型代码只能在隔离解释器内调用宿主只读工具，不能碰文件/网络/进程 |
| 范围校验 | 工具读取受快照范围、pin、去重、读账本与预算约束 |
| 源码边界校验 | 漏洞候选必须引用实际读过的源码行，未读行不通过 |
| 数据流证据链 | 要求"输入 → 传播 → 危险操作"完整链 |
| POC 自动验证 | 隔离 runner 实际执行，观测正常/攻击两侧 |
| Planner 复核 | 第二个模型读同一份证据，confirmed/contested 表态 |
| 固定启发式隔离 | 固定 SQL/XSS/命令执行启发式不用于目标任务 |
| 结论状态机 | achieved/continue/no_evidence/blocked + 未决保留 |

# 第 6 章　模块三：LLM 漏洞推理挖掘逻辑设计

> **模块核心目标**：梳理 LLM 辅助漏洞挖掘的核心推理逻辑，明确 AI 的工作原理与判定机制。

## 6.1　三级分层推理设计

### 6.1.1　推理链路

```text
第一层：代码语法检测
  → 依据 tree-sitter 语法索引/文本索引定位代码结构（函数、类、调用关系）
  → 建立项目结构概览与高置信入口

第二层：漏洞语义识别
  → Worker 读取具体源码窗口
  → 识别"输入来源 / 传播路径 / 危险操作(sink)"语义
  → 判断是否存在可利用的数据流

第三层：业务安全风险判定
  → 结合利用前提(登录态/资源属主/CSRF/业务状态)
  → 判定漏洞类型、可利用性、影响范围 → 定级
```

### 6.1.2　检测重点逐层拆解

| 层级 | 检测重点 |
| --- | --- |
| 语法检测 | 文件结构、函数边界、静态 include/依赖、路由定义、入口定位 |
| 语义识别 | 污点源（上传、请求参数、Cookie、数据库读回）、传播（拼接、编码/解码）、Sink（SQL 语句、命令、HTML 输出、文件写） |
| 业务风险 | 鉴权边界、资源属主、业务状态、会话/Cookie 配置、敏感配置、危险依赖 |

## 6.2　漏洞量化判定标准

### 6.2.1　统一判定条件

针对每类漏洞制定明确可落地的判定条件，作为 LLM 挖掘和人工核验的统一依据（详见第 5.2 节分场景判定规则）。核心共性标准：

- **存在性**：有源码行号证据支撑的"输入 → 传播 → 危险操作"链；
- **可利用性**：存在触发条件（参数可控、可达、有前置状态）；
- **影响**：可导致数据泄露/篡改/未授权访问/代码执行等明确后果；
- **风险等级**：以 CVSS 3.1 基础分四档（低/中/高/严重）量化。

### 6.2.2　结论状态机

| 状态 | 含义 |
| --- | --- |
| achieved | 目标相关漏洞已达成 |
| continue | 需继续追踪 |
| no_evidence | 无证据 |
| blocked | 受阻 |
| 未决(pending) | 预算/回合耗尽或共享尝试，不标完成 |

## 6.3　结论状态与预算容错

- 每个动态任务保存领取、尝试、用量、已读行号、结构化结论；
- 预算（单次/整次）冻结，到期停止新请求/工具/任务；
- 穷尽与终审条件分别成立；未决方向不标完成；
- 运行可在回合边界暂停并原样继续。

## 6.4　预容错设计

### 6.4.1　易漏报场景与规避

| 漏报场景 | 预判规避思路 | 实测效果（Lab30 定稿） |
| --- | --- | --- |
| 跨文件/二次注入 | 项目任务图跨文件交接 + 依赖摘要，专门流程见第 10.4 节 | 部分有效：二次注入（真值 28）命中，跨文件命令注入（真值 24）与跨文件 SQLi（真值 23）仍漏报 |
| 框架路由动态加载 | 记录未解析动态关系为未决上下文，不当作默认起点 | 有效（未产生相关误报） |
| 业务逻辑漏洞 | 注入业务上下文，Worker 追问历史结论 | 部分有效：越权 IDOR（16）、金额篡改（19）、批量赋值（30）命中；CSRF（14）、Cookie 权限绕过（17）、请求头认证绕过（18）漏报 |
| 大库覆盖不足 | 覆盖统计 + 前沿派发，未读模块显式标注 | 有效：覆盖复核 61/61、pending 0 |

### 6.4.2　易误报场景与规避

| 误报场景 | 预判规避思路 | 实测效果 |
| --- | --- | --- |
| 静态导航当证据 | 证据必须来自 worker 实际读过的源码行 | 有效 |
| 防护到位判为漏洞 | 判定标准要求"可被利用" | 有效（定稿 FP=1，为同一位置 LFI/RFI 类别判定偏差） |
| 单凭严重性/POC 存在 | 不据此判定漏洞成立 | 有效 |
| 隐藏推理当结论 | 只保存审计依据摘要，不保存思维链 | 有效 |

> 6.4 节为预容错设计的**反向验证**：用定稿运行的实测盲区逐条核对预判是否成立——这正是评分文件"预容错设计"要求的实证支撑。未缓解的盲区（CSRF、跨文件链、弱加密）进入第 10.4 节专项流程与第 11.1 节缺陷登记。

## 6.5　风险量化定级：CVSS 3.1 基础分

- 漏洞由宿主根据八项有证据支持的基础指标计算分数，划低/中/高/严重四档；
- 项目台账支持指标预览、人工修订与独立评分历史；
- 完整向量与已冻结指标依据进入详单；0.0 与待评分分别显示；
- 定稿实测：CVSS 分数绝对误差与等级准确率见 7.3.3 节。

## 7.2　POC 验证实操流程

### 7.2.1　标准流程（人工运行视角）

```text
LLM 生成 POC 脚本 → 脚本预处理(适配环境/参数) → 本地运行
  → 观测执行结果(是否成功触发漏洞) → 记录正常/攻击两侧观测
```

### 7.2.2　平台自动运行流程（阶段三起）

# 第 11 章　方案缺陷与优化方向

## 11.1　已实测缺陷

基于阶段三 Lab30 全量验证与 Prompt 横向实验，已识别以下实测缺陷。**本节只收录有证据的缺陷，每条均附定位与修复状态**。

### 11.1.1　框架确定性缺陷（均已定位、离线复现并修复）

| 缺陷 | 现象 | 根因 | 修复 | 证据 |
| --- | --- | --- | --- | --- |
| Planner 态势 16 KiB 上限 | "全量 + POC auto"组合下运行必然失败；受保护闭包事实达 67,501 / 30,208 字节（溢出 51,117 / 13,824） | 态势上限不裁剪 POC 验证记录 | 态势摘要化 + 分页只读工具 + 作业额度预约 + 覆盖复核收束 + 精确判重（2026-10-27 交付；后端 1215 项、前端 79 项测试通过） | `deliverable/lab30-validation-2026-10-26/02-full-audit/framework-defect/reproduce_planner_ceiling.py` 历史离线复现（需对应原始输入） |

| 上下文压缩预算缺陷 | 摘要请求吃掉阶段最后一个响应，压缩后的请求从未真正发出 | 压缩器发起摘要前未确认预算 | 摘要前先确认两级预算；只剩一个响应时确定性裁剪并记 `context_summary_failed(reason="budget")` | `backend/tests/test_context_budget.py`、`test_code_model.py` 离线回归 |
| 去重二档过严 | 同一 sink 换句话描述即无法合并（D=29→28），如 `ops/template-render.php:3` 5 条主张 | `normalise_sink` 只做 NFKC/大小写/空白归一，等同要求逐字相同 | 二档改按 `sink_similarity`（Jaccard）判重；对中文换述仍偏严属已知残余限制 | commit `37dcee0` 及第二轮闭环对照 |
| 覆盖复核被 blocker guard 截断 | 最后 7 条待复核路径没有机会被显式 skip | blocker guard 先于覆盖复核判定 | 改为先 POC 与覆盖复核、后阻塞停滞判定；支持原子缩小并重开 blocked 任务 | 第二轮闭环 pending 7→0 |

### 11.1.2　审计能力边界

- **非 PHP 语言**：仅做纯文本行索引，无 tree-sitter 语法索引，跨语言符号解析缺失；
- **跨语言/完整污点分析缺失**：不做完整跨项目污点分析，依赖 LLM 语义 + 项目图近似；
- **上下文窗口限制**：长文件切片、跨文件上下文仍可能丢失细节，导致漏报；
- **跨文件污点链仍为盲区**：定稿运行中跨文件命令注入（真值 24）与跨文件 SQLi（真值 23）漏报；横向实验中强调跨文件的 W2 策略在该链上仅 2/3，不优于基线——说明该问题需要的是任务图层面的依赖交接，而非更长的指令；
- **业务语义型与知识依赖型缺陷为系统性盲区**：CSRF（真值 14）、Cookie 权限绕过（17）、请求头认证绕过（18）、弱加密（10）在定稿轮漏报；其共性是"缺陷表现为某个防护的缺失"，而模型擅长判断"存在什么"、不擅长判断"该有什么却没有"；
- **定级弱于检出**：分数误差以高估为主（7.3.3 节），开放重定向与 JWT 类高估显著。

### 11.1.3　验证边界

- runner 无崩溃后"恰好执行一次"协议；
- 自动验证范围仅限本地 Lab30，非 Lab30 项目如实标 not_applicable；
- 模型自述得不到作业支撑时降级为 inconclusive；
- **结果方差**：历史同配置两次全量跑 Recall 为 0.867 与 0.300——单次运行成绩不足以支撑结论，必须多轮配对并显式报告标准差。

P25 改为 Lab30 收尾问题登记：现象、代码/实验版本、日志定位、原因、处理状态和必要回归。优先登记三项后端测试失败、统计冲突与证据缺失；没有新增框架缺陷可写“未新增”并给检查范围，不要求为了填表制造缺陷。
