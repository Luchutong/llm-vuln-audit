## 1. 统计口径与方法

### 1.1 生产规则（逐字复用，未做任何修改）

- **清洗 `_clean`**：原始字节永不改变，清洗只改变模型投影。
  - 非安全注释（未命中 `SECURITY_COMMENT` 的 comment 节点）→ 用等长空格替换，记 `irrelevant_comment`；
  - 命中安全关键词（security/sanit/escap/validat/auth/csrf/inject/xss/sql/input/password 及中文 安全/漏洞/过滤/转义/验证/权限/密码）的注释**保留**；
  - 空行（且不在字符串字面量内）剔除，记 `blank_line`；
  - 字符串字面量（`STRING_TYPES` 节点）受保护，不参与空行剔除。
- **切片 `_slice`**：`MAX_SLICE_LINES=200` 行、`MAX_SLICE_BYTES=16 KiB`、`SLICE_OVERLAP_LINES=24`；边界类型 `unit_end / statement_boundary / forced_line_boundary / forced_byte_boundary`；强制字节回退且不切断 UTF-8 序列。
- **解析 `_index`**：tree-sitter（PHP 语法）提取函数/类/包含/调用与顶层单元，记录 parse errors。

### 1.2 两套统计范围

| 范围 | 含义 | 是否去重 |
|---|---|---|
| 文件级（file level） | 对**整个文件**直接调用生产 `_clean`，反映清洗的真实效果 | 按行去重，权威 |
| 切片级（slice level） | 以冻结快照中的每个 unit（实际喂给模型的切片）为单位，含 24 行重叠 | 不去重，等于真实请求成本 |

> 方法学说明：本报告文件级数字通过对整个文件直接调用生产 `_clean` 得到，而非从切片结果重建。已验证"从切片重建"会在切片边界产生伪影（详见 4.3），故不采用。

### 1.3 Token 口径

- **LLM token**：`tiktoken` 的 `cl100k_base` BPE（GPT-4 / GPT-3.5 同款编码），反映真实上下文成本；
- 同时报告物理行数与字节数，便于交叉核对。

### 2.2 关键现象解释

1. **行数大降、token 小降（phpMyFAQ：行 -19.84%，token 仅 -6.11%）**：被剔除的空行几乎不承载 token，注释行的 BPE token 密度也远低于代码；承载绝大多数 token 的代码行全部保留，因此 token 节省幅度显著小于行数节省幅度。
2. **注释替换 ≠ 整行删除**：169,518 次注释事件中，约 3,635 次是**行内注释**（如 `$x = 1; // note`），注释被空格替换但代码保留、该行不删除；其余为整行注释（整行删除）。全库仅 2 行产生多条 omission 事件（315,095 事件对应 315,093 个唯一行）。
3. **Lab30 清洗零剔除**：该靶场为紧凑风格代码，整个文件级无空行/非安全注释可去，清洗前后完全一致。

### 3.3 重叠与实际请求成本

| 指标 | Lab30 | phpMyFAQ |
|---|---:|---:|
| 切片总数 | 72 | 69,305 |
| 含重叠（overlap>0）的切片 | 0 | 4,177 |
| 切片 token 总和（实际请求） | 13,508 | 24,636,835 |
| 重叠/边界额外 token | -8 | 1,624,301 |

- phpMyFAQ 因 24 行重叠，实际所有模型请求的 token 之和（24,636,835）比文件级去重值（23,012,534）多 1,624,301（约 +7.1%）；
- 一个值得注意的净效应：**清洗节省的 token（约 150 万）几乎被重叠增加的 token（约 162 万）抵消**，故切片总 token（2,463 万）与原始 token（2,451 万）基本持平；
- Lab30 无重叠，切片总 token 与文件级仅差 -8（BPE 在切片边界的微小合并效应）。

### 3.4 零保留行切片

phpMyFAQ 有 **11,471 个切片清洗后零保留行**（字节范围非空，内容整段为注释/空行，典型如全注释的 top_level 片段），另有 1 个字节范围为 0 的空切片；这些切片不向模型提供有效代码，建议在调度时跳过以节省调用。

## 4. 直方图与重要现象

### 4.1 直方图

- Lab30：`D-C03_lab30_切片直方图.png`（行数、token 双分布，均值 5 行 / 188 token）
- phpMyFAQ：`D-C03_phpmyfaq_切片直方图.png`（均值 19 行 / 356 token，右尾长，少量大切片接近 14K token）

### 4.2 依赖目录识别现象（重要，须如实记录）

- 生产规则的 `EXCLUDED_DIRECTORIES` / `DEPENDENCY_DIRECTORIES` 包含 vendor、node_modules、dist、build 等，但**不包含 `libs`**；
- phpMyFAQ 将第三方依赖置于 `phpmyfaq/src/libs/`，其下共 **8,454 个 PHP 文件**，因目录名不匹配，仅 **15 个**文件（路径中另含 build/Cache 等目录名者）被标记 `dependency_tree`，其余第三方依赖被当作项目自身代码处理；
- 影响：本次统计的代码规模与切片包含大量第三方库代码。这是生产规则与该项目目录约定的真实交互结果，未做人为调整，后续评估命中/漏报时须显式区分"自研代码"与"libs 依赖"。

### 4.3 切片边界伪影（方法学校验）

从切片结果重建文件级统计会产生伪影：Lab30 切片级出现 3 条 `blank_line` 记录，但逐行核对其完整内容分别为 `}]`、一个完整函数、以及含 `shell_exec($this->command)` 的方法（`dispatch_job.php` 第 4 行），均非空行——只是被切片边界切到了相邻片段。若误判为空行剔除，可能漏掉真实命令注入点。这验证了本报告采用"整文件直接 `_clean`"权威口径的必要性。

## 5. 结论

1. **清洗对大型真实项目有效**：phpMyFAQ 物理行数减少 19.84%，以极低的 token 损失（-6.11%）剔除了大量注释与空行，且安全注释与字符串字面量得到保留；对紧凑靶场 Lab30 则无冗余可去（0%）。
2. **切片保证不超长**：两目标切片均在 200 行 / 16 KiB 内，绝大多数在符号自然边界结束；phpMyFAQ 仅 5.3%（3,642/69,305）为需上下文的强制切片。
3. **重叠成本可控但真实存在**：重叠带来约 7.1% 的额外 token，与清洗收益基本对冲；11,471 个零有效内容切片建议调度时跳过。
4. **须显式处理依赖口径**：`libs` 不被识别为依赖树，8,454 个依赖 PHP 纳入了统计，后续指标须区分自研与依赖。
