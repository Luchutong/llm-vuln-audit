调查日期：2026-11-01，时间均为 Asia/Shanghai。代码基线：`main@7a467bd`，同时保留当前工作树的运行页改动。

## 1. 结论与优先级

建议围绕四个结果推进：**任务始终围绕用户目标；覆盖能表达还没查清的风险；模型少花请求修补结构；报告能直接交给开发复现和修复。**

| 优先级 | 工作 | 实际收益 |
| --- | --- | --- |
| P0 | 统一完成口径和目标相关性合同 | 避免关闭 POC 却永远只能生成阶段报告，以及定向任务扩展为全站审计 |
| P0 | 阅读版 Markdown、漏洞报告汇编、单条漏洞导出 | 先修复已有事实没有被正确表达的问题，形成可交付文档 |
| P1 | 风险义务覆盖和跨文件证据链 | 降低“文件读过了，但关键风险没查到”的情况 |
| P1 | 宿主提供结构化提交骨架、前移候选整合 | 减少格式纠错、重复验证和终审返工 |
| P1 | 实验判别合同与修复交付检查 | 提高动态验证的可解释性，让接受的漏洞具有可操作的修复材料 |
| P2 | 知识路由、上下文复用、按证据收益分配探索额度 | 改善每次请求的产出，以受控对照验证收益 |

暂停恢复、POC 关闭门禁、身份登录、幂等占位和终审配额回收已经存在。后续方案应在这些基础上增强能力。

需要区分的口径：

- 最新一次中断不是预算耗尽，也没有证据支持再次认定为过去的“执行者退出但仍 running”故障。
- `2969bcf2` 的历史验证尝试为 25 次：24 次 verified、1 次 inconclusive；规范当前版本为 22 条动态确认。验证尝试次数、规范漏洞数和离线 TP 是不同指标。
- 本次未重跑真值评分。已有第七轮闭环记录为 TP 22、FN 8、F1 0.8302；第六轮 TP 27。这表明检出仍会波动，不能凭两次运行断言某个改动导致召回下降。[闭环记录](lab30-closure-run.md)
- 冻结报告的应审文件口径是 61；`2969bcf2` 中读取 59、读取或带理由跳过后复核 61。其他宿主统计可能以全部 69 个文件为分母，不能合成一个“审计覆盖率”。

### 2.2 目标相关性缺口

上传任务的目标为“任意文件写入、路径穿越或危险文件上传”，18 条接受结论中却包含公开目录 SQLi、反射 XSS、开放重定向和 Cookie 角色绕过；冻结结论没有说明它们如何构成上传利用链。

最新 SQLi-only 任务也产生了弱类型兑换和批量赋值候选。不能仅凭类别名判断所有跨类别结论都无关，但现有合同没有要求给出与目标的证据关联。

这些运行都是 fresh。fresh 表示不直接继承历史结论，并不表示每条结果都新建了项目台账；同源码上的重新发现仍可能关联既有台账 ID。

### 2.3 完成语义不一致

`2bf893de` 的运行与宿主摘要均为完成，文件/方向结算完成，18 条全部静态终审接受；冻结报告却是阶段报告、`audit_complete=false`。

根因是 [`report_bundle.py::_run_outcome`](../backend/audit/report_bundle.py) 无条件要求 `verification.pending == 0`，把关闭 POC 的 18 条未动态验证结论全部计入未完成。静态接受与动态确认本来就应独立，这属于策略与报告契约不一致，需要单独修复。

### 2.4 结构纠错与验证成本

- `2969bcf2` 有 21 次输出校验拒绝：缺 `rationale_summary` 9 次、缺正式动态复核 5 次、版本/双侧观测不匹配 4 次、批次版本变化 1 次、其他 2 次；另有 18 次解析错误和 4 次 Planner 回合失败。
- 可复现事件包括 `66014、66032、66064、66072`；失败回合事件为 `66075、66153、66174、66195`。
- 最新运行 24 次请求中有 5 次解析错误、2 次输出拒绝；首个 worker 连续 3 次没有代码块，随后才进入判定。这批事件应作为动作协议夹具。

## 3. 审计能力改进

### A1：冻结目标相关性合同（P0）

源码可读范围与漏洞关注范围分别表示：允许阅读整个 ZIP，不代表任意类型的发现都可用于达成定向目标。

建议在冻结任务中增加 `audit_focus`，记录目标功能/入口、关注风险、允许的辅助利用链与范围政策。每项保留原目标片段、显式 `scenario` 或用户选择等来源；原始目标仍是权威。任务和发现引用 `objective_ref`，并提供：

| 关联 | 行为 |
| --- | --- |
| `relevant` | 直接对应目标，能够支撑本次目标和主报告 |
| `supporting` | 是目标利用链的必要前提，须引用实际跨文件关系 |
| `incidental` | 有效旁路发现，保存证据和台账，单列附带发现 |
| `unresolved` | 相关性证据不足，保留待判断，不能支撑目标已达成 |

要求：

1. 不能以标题关键词、漏洞类型或文件夹直接代替相关性判断；上传链可以经过鉴权、存储和部署配置。
2. 旁路发现不删除、不伪装误报，也不自动扩大主任务或让定向任务成功。
3. 显式 `scenario` 应有宿主范围约束；自由文本目标的结构化提取保留依据，含糊目标先标记，不能默默扩大为所有类型。
4. 新合同仅对新任务生效；历史运行展示原目标及“未记录相关性”，不批量改写处置或台账。
5. 不能靠模型自行标记 `relevant` 通过门禁。宿主验证真实引用、路径、义务和依赖归属，相关性的语义判读进入现有独立终审；缺证、自相矛盾或未复核时不能支撑目标达成。确定性规则不能独自证明自由文本目标的全部语义。
6. `supporting` 不能独立达成目标，必须链接目标主张或明确待查义务，并说明必要依赖。共享 bootstrap、同一目录或名称相近不构成利用链；例如无关 SQLi 只有在证实影响上传配置/路径等条件后才可能成为辅助风险。

入口：`schemas.py::TaskSpec/PlannerTaskProposal`、`agent.py::_validate_planner_decision`、任务/发现持久化与 `report_bundle.py`。

### A2：把文件覆盖和风险义务分开（P1）

[`coverage_review.py::review_state`](../backend/audit/coverage_review.py) 当前检查路径是否读过或有跳过说明；它不是函数、数据流或漏洞风险的穷尽证明。

为深度全量审计增加可选的风险义务，基于真实源码信号建立：

```text
入口或业务边界 → 外部输入/持久化读回 → 敏感操作 → 攻击前身份与状态
```

每项至少保存来源坐标、目标关联、所需辅助文件、当前状态和结算证据。状态可为已支持、已排查未证实、不适用、受阻或待执行。

- 由实际调用、危险操作、认证边界和配置派生义务；不生成“每文件 × 所有漏洞类型”的笛卡尔积。
- 仅对新任务冻结的深度策略启用；保留既有 `coverage_review` 兼容口径。义务具有稳定身份、来源坐标、去重键和有界分页，必做/建议由冻结策略与目标关系决定，不允许每轮凭散文无限增殖。
- 读过文件头不能自动结清文件末尾的敏感操作；“已交给另一个任务”不能代替该任务的结算事实。
- 动态调用、未知框架路由、二次读回关系保留为明确缺口，不臆造完整调用图。只让与当前目标相关的必做义务阻止完整收束，不让索引中任意未知关系永久阻塞全部任务。
- 全量深度模式的必做义务未解决时不得宣称完整；预算耗尽仍正常输出阶段报告。
- 快速目标模式保留原语义；定向模式只让目标相关必做项阻止收束。跳过保留理由并明确不是安全结论。

优先增强现有 PHP 索引的有界调用者/被调用者/include/共享辅助函数查询。结构化流节点分别标明输入、转换、防护、持久化、读回和 sink，绑定真实行号；导航索引不能代替 worker 取证。

### A3：宿主提供提交骨架，模型填写判读（P1）

从当前批次生成角色专用、符合 schema 的最小提交对象：宿主提供准确的 item/finding/revision/verification 引用和合法枚举，模型填写处置、根因判断、正常/攻击解释及 `rationale_summary`。

- 结构校验前置；一次列出当前提交的全部字段问题，并给出当前版本的正确样板。
- 首次格式失败就反馈最小合法动作，不反复发送完整工具手册。
- 补齐字段不能替换证据、版本或终审依据；批次输入变化后显式重取。
- 保留全部证据校验、同版本复核和有界纠正；宿主不能替模型自动填写“已验证”或接受理由。
- 提供引用 ID 不等于已读取对应证据。宿主不能预填“已完整读取”、正常/攻击的语义判读或候选差异判断，仍检查真实读取区间和当前版本。
- 使用真实事件夹具分别验证结构错误减少，以及过期版本、伪造引用和缺少对照仍被拒绝。

Worker 已有探索/判定两阶段和发布预留；`agent.py:2835` 的探索额度受 `worker_explore_responses` 控制。可研究按新证据收益与跨文件复杂度分配探索额度，并公开实际阶段限制；这不是整次预算重置，不能通过延长纠错变相突破总额。

### A4：候选整合前移与可判别实验（P1）

复用已经存在的按需 integration 批次，先量化当前整合触发时机与重复 POC，再优化 worker 小批提交后的选择，让唯一、可解释的同根因候选更早整合。最终 D=0 表明后置整合已有效，优化目标是减少重复工作，而非扩大模糊合并。

同根因比较依赖主操作坐标、流和适用前提。一个文件同一行仍可能有两个不同操作或身份风险，不能仅按位置合并。

每项 POC 明确要证明的安全属性，并保存实验清单：

- 攻击前角色、资源属主、初始业务状态、登录/CSRF/配置前提；
- 正常对照、攻击变量、预期判别条件，以及实际成功/失败观测；
- 数据篡改的读回、越权的攻击前权限、XSS 的执行证据、竞争问题的并发与状态不变量；
- 目标版本、实验身份、结论修订及实际作业引用。

复用现有登录、隔离上下文和检查点机制；不同身份的会话、可变状态及实验产物不得混用。不确定提交继续查询原作业，无法确认时保留未决。HTTP 200、退出码 0、页面长度差或高权限成功均不能单独作为漏洞成立证据。

### A5：修复材料与上下文效率（P1/P2）

`2969bcf2` 的 23 条接受结论中有 3 条没有修复建议，`2bf893de` 有 2 条。增加交付材料检查：根因对应的代码修改位置、修复原则、复测步骤和回归条件。

“漏洞是否成立”和“交付材料是否完整”单独记录。缺少修复建议应显示待补充和交付待办，不删除已证实漏洞，也不在导出时临时请求模型编造修复。

知识路由改为通用方法加命中任务/源码信号的专题。当前 [`knowledge.py`](../backend/audit/reuse/autocve/knowledge.py) 中语言命中即可获得基础分，PHP 专题容易整体加载；应记录路由理由、版本和字节量。共享不可变源码块和导航结果可按快照缓存，但每个 worker 仍需建立自己的读取/引用授权。

## 4. 完成性契约修复（P0，独立于排版）

新增明确的分维度结果，例如：

```text
execution_status          执行是否结束/中断/取消
focus_complete            本次目标相关工作是否结算
source_review_complete    对冻结范围的文件/方向复核
dynamic_verification      未启用 / 可选且部分完成 / 必须完成的验证是否满足
final_review_complete     当前结论版本的独立终审是否完成
delivery_readiness        报告材料完整 / 缺失材料及原因
```

总体完成性按冻结策略计算：

- `off`：新增自动验证调用和作业为 0，报告明确“未启用”；保留源码、版本和目标兼容的历史/继承验证及来源，不能把未执行标成已验证，也不能把关闭验证解释成清零历史状态。
- `auto`：不要求至少一条 verified，缺少动态环境不直接判任务失败；静态接受、动态未决及适用限制均保留，已有 verified 仍须满足同版本独立复核。
- `required`：沿用当前至少一条源码、结论和目标兼容的有效动态验证门槛，并满足独立复核、目标/覆盖/方向/终审门禁；不擅自收紧为每条漏洞必须动态成功。若任务另有更强验证要求，则按冻结要求执行。
- 快速目标完成与全量复核完成使用不同标准，分别表述；中断、取消和受阻不变成安全结论。

将 policy/schema 版本冻结在新运行中，统一 run、宿主摘要、终审、页面与导出。历史事实不回算；旧报告保留当时口径，阅读版标明历史政策及各维度事实。

### 5.2 三类报告，共用一个事实源

| 产物 | 用途 | 内容 |
| --- | --- | --- |
| 审计执行报告 | 项目负责人快速判断结果与后续安排 | 源码包/目标、策略完成性、关键计数、精简漏洞表、覆盖与未完成动作、追溯附录 |
| 漏洞审计报告汇编 | 单独交付本次所有漏洞 | 同一套漏洞详单按接受/待审/存疑分区，区内按严重性稳定排序，含目录与锚点 |
| 单条漏洞审计报告 | 直接交给某个开发复现和修复 | 一条规范结论的完整前提、证据、复现、终审、评分、修复及附件 |

执行报告不重复铺开全部 HTTP 原文、脚本和历史尝试。汇编复用单条模板；下载完整证据包时附带每条 Markdown。单独下载的报告不应依赖只能在 Web 页面解析的相对 API 地址。

清单建议为：编号、漏洞及主位置、严重程度/分值、动态验证、独立终审处置、详情锚点。短编号与 canonical ID 的映射在同一冻结运行的所有视图中保持一致，不因排序或导出类型重新编号。

源代码引用仍取冻结快照原文。正文可摘录最少必要片段，其他上下文进入详单/附件，以冻结时实际保存的内容为限；历史片段已截断时说明缺口，不能补读当前文件冒充当时原文，也不能用模型生成的“近似代码”替代证据。修复、输入步骤和判断理由不做静默截断；超长原始作业日志转附件并给出引用。

### 5.3 单条漏洞模板

```markdown
# C-03 漏洞标题

源码包：……；结论版本：……；证据快照：……
CVSS 3.1：分值、严重程度；动态验证：……；独立终审：……

## 影响与受影响位置
简述攻击者能够做什么、涉及哪个入口、已经证明和仍未证明的影响。

## 利用前提
登录角色、资源属主、CSRF/会话、初始状态、必要配置。

## 根因与源码证据
输入位置 → 传播/持久化读回位置 → 危险操作位置。
每段引用实际路径行号，附最少必要的快照源码。

## 复现与实际验证
1. 环境和登录准备。
2. 正常请求及其作用。
3. 攻击请求，仅改变需要检验的变量。
4. 实际观测、读回或浏览器证据，与预期差异分开。

无执行记录时写明“以下为待执行脚本”，不声称已经复现。

## 终审结论与限制
独立终审处置、真实理由、适用版本；动态复核另列。

## CVSS 3.1 依据
完整向量、各指标理由、评分版本；未知信息明确标注。

## 修复建议与复测
根因对应的改动位置/原则、正反例及回归条件。
缺失内容记为待补充，不临时生成新结论。

## 来源与附件
任务、台账/发现身份、快照和修订、源码/观测/脚本索引及哈希。
```

静态接受不写成动态确认；存疑/排除项保留原因并单列。没有规范漏洞时说明“本次未形成可交付漏洞结论”，不能写成“项目安全”。

## 6. 单漏洞导出与历史兼容

### 6.1 建议接口

保持已有 API 的默认返回和历史归档下载，增加显式视图及单漏洞导出：

| 接口 | 语义 |
| --- | --- |
| `GET /api/runs/{run_id}/report?format=markdown\|json\|zip&view=audit\|vulnerabilities\|archive` | 执行阅读版、漏洞汇编或归档原件；省略 view 保持旧行为 |
| `GET /api/runs/{run_id}/canonical-findings/{canonical_id}/report?format=markdown\|json\|zip` | 从该运行冻结事实导出一条规范结论 |

`canonical_id` 在字段语义上区别于运行 finding ID 和项目台账 ID；字符串值可能与台账 ID 相同。服务端先读取父运行冻结 `canonical_findings` 做归属解析，不能直接用字符串查当前台账。

视图与格式的返回合同：

- 省略 view 或指定 `archive`：合法格式保持原响应字节、内容和 ETag。
- `audit/vulnerabilities + markdown`：分别返回执行阅读版或漏洞汇编。
- `audit/vulnerabilities + json`：使用版本化派生文档，明确 `view、scope、source_hashes`，不覆盖原事实及其 `quality_result`。
- ZIP 在 manifest 中指定 `main_document`，下载漏洞汇编时主文档不能仍指向执行摘要。

- 运行结束后才提供正式冻结报告。运行中若将来支持预览，必须标注草稿，不复用正式终审标签。
- 台账页默认下载能精确匹配结论修订/评分修订的冻结来源。没有匹配版本时显示“当前版本暂无冻结报告”，允许显式选历史任务，不能把旧报告冒充当前版本。
- 当前台账报告与历史运行冻结报告是两种性质；首期以运行冻结版本为准，活跃台账即时快照另行设计。
- 漏洞不属于该运行或不存在返回 404；未冻结返回 `409 report_not_ready`。缺少可用冻结事实/input 的旧版运行保留归档下载，派生导出返回 `409 legacy_facts_unavailable`，不得借用活跃台账或 `_attach_final_review` 重建历史。非法 format/view 返回明确校验错误。
- 单条 JSON 的计数范围为该条报告；父运行统计放 `parent_summary`，不能让“单条报告 23 条漏洞”成为新的口径混淆。

前端在报告抽屉提供执行报告/漏洞汇编选择；运行发现和独立漏洞详情增加下载入口。沿用现有路由和组件，不重新引入运行页悬浮统计窗。

### 6.2 冻结与渲染版本

现有 [`frozen_reports.py`](../backend/audit/frozen_reports.py) 返回保存的报告字节；[`review_store.py`](../backend/audit/review_store.py) 有输入/输出不可变触发器。直接修改 renderer 不会更新已经冻结的报告。

实施必须：

1. 新运行使用版本化事实契约和新 renderer；历史归档 Markdown/JSON/ZIP、hash/ETag 原样保留。
2. 历史阅读版从已保存事实生成新呈现，标明“基于历史冻结事实重排版”，不重新终审或回算历史完成性。
3. 旧事实未投影的任务目标/源码包名称，只能从对应冻结 input 补入版本化呈现元信息；不能查询当前项目名称或最新台账拼接历史。
4. 新产物记录 frozen input hash、facts hash、原归档 output hash、renderer/template 版本及本产物 hash；缓存按这些来源和视图/漏洞身份区分，避免污染原件。
5. 单漏洞按其规范实体的证据/验证/终审引用闭包筛选，只收相关源码、POC 和产物。历史继承验证保留真实来源、身份与版本，不能混入其他漏洞的作业或整个项目附件。
6. 原始事实质量结果保留；新布局使用独立的渲染质量记录，不能通过重排版修改历史 `quality_result`。
7. 运行删除时同步清理派生报告及缓存映射，遵循现有来源/删除规则，不能由缓存复活已删除的运行内容。

建议包结构：

```text
report.md                       # 执行阅读版
vulnerability-report.md         # 漏洞汇编
findings/C-03.md                 # 每条独立报告
final-review.json               # 对应冻结事实
manifest.json                   # 身份、来源、版本及哈希映射
render-quality.json             # 新模板的呈现校验
evidence/...                    # 源码、正常/攻击观测与脚本
```

上述为完整报告包。单条 ZIP 仅保留该条报告及其引用闭包，用 `finding-facts.json` 保存版本化投影、`parent_summary` 与父事实哈希，不打包父运行全量 `final-review.json` 或其他漏洞正文。Markdown、代码围栏、表格管道、标题/锚点、Unicode 文件名和压缩包路径都要正确处理；脚本/令牌等原始证据与正文脱敏显示的来源、哈希分别标记。

### 6.3 同步修改报告质量门禁

当前 `report_quality.py` 依赖固定七章标题和 `- 已接受漏洞：N` 正则。换模板时必须引入按报告类型/模板版本校验的契约，防止布局变化被误判交付失败。

可先生成结构化报告文档，再分别校验数字、对象归属、状态、必需章节和引用闭包；Markdown 渲染后检查锚点、表格与围栏。原 `quality_result` 和历史发布状态原样保留；历史事实若需复核，使用原政策/引擎版本并单独保存结果。新模板只生成独立 `render-quality`，不用新规则反算旧发布性，也不用隐藏文本、伪造小节或放宽校验凑通过。

## 8. 验收标准

### 8.1 确定性与模拟验收

| 编号 | 通过条件 |
| --- | --- |
| T01 | POC off 下静态接受与本轮策略完成可正确表达；未执行不自动变成 verified，兼容的历史有效验证不被清零 |
| T02 | auto 环境不可用、required 未达门槛、暂停、中断、取消分别保持正确口径 |
| T03 | 上传任务里的无关 SQLi 即使自标 relevant 也不能支撑达成；共享 include 伪装必要依赖不能通过，真正跨文件上传链仍可纳入 |
| T04 | SQLi-only 的旁路弱类型风险保留为附带发现，不静默删除或变成 SQLi |
| T05 | 只读文件头不能结清末尾 sink；目标相关必做链路未解决时不完整收束，非相关未知关系不永久阻塞 |
| T06 | 结构骨架减少缺字段请求；模板有正确 ID 但未完整读证据、过期版本、伪造源码或缺对照仍被拒绝 |
| T07 | 读取、任务分配、显式跳过和风险排查结果分别计数，不混用 61 与 69 的分母 |
| T08 | 正文展示实际独立终审理由；无动态记录不被描述成“未进行独立终审” |
| T09 | 脚本待执行、实际观测、历史继承和当前动态确认标识清楚；缺修复进入待办 |
| T10 | 清单窄表、CVSS 3.1 完整向量、多行步骤、反引号/管道和长路径均正确渲染，无空 POC 句、NaN 或技术对象 repr |
| T11 | 审计报告、汇编、单条、JSON 和 ZIP 按各自范围统计一致，编号/锚点可追溯；单条投影不含其他漏洞正文 |
| T12 | 单漏洞不能越运行、跨修订或打包无关附件；来源/文件缺失有明确信息 |
| T13 | 更正台账、重评分、删除来源运行后不混入另一版本内容；已有历史原件仍遵循其存档/删除规则 |
| T14 | 同一冻结输入与模板产生确定性导出；历史原始字节、quality_result 和 hash/ETag 不变；缺事实时不查询可变记录重建 |
| T15 | 零漏洞、仅待审、仅存疑、缺字段和旧 schema 均能生成诚实可读报告 |
| T16 | 模拟浏览器验证下载、快速切换、错误重试、深浅主题及移动布局，不启动模型/runner |

后端执行 `uv run --extra dev --frozen pytest tests/ -q`；前端执行 `npm test`、`npm run build`，扩展现有报告、台账和运行页模拟脚本。

### 8.2 能力效果评估

结构回放不能证明召回提升。后续真实评测需用户另行启动，冻结同源码、模型配置、目标范围/完成策略、预算及 POC 初始状态，交错运行顺序，至少进行三组配对作为初步证据；条件允许时增加样本并报告方差，不能以三组承诺显著提升。

分别评估目标相关率、离线真值召回/重复、证据有效率、格式纠正开销、输入/输出 token、耗时、首次有效发现/首次验证发布时间、终审请求与报告盲审通过情况。每百请求产出仅统计同一目标内、经独立终审接受、按现有身份去重的本轮独立取证结论；继承、附带发现和未决候选分开统计，不用它们虚增收益。真值和漏报清单只进入离线评分，不进入审计 agent 的上下文。

报告盲审沿用 [report-blind-review.md](report-blind-review.md)，重点检查根因、登录权限、观测充分性、CVSS 3.1、修复与未决披露。不能通过隐藏失败、合并不相同漏洞、放松证据校验或删改真实历史来提高指标。
