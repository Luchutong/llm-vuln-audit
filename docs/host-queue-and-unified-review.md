# 宿主调度、动态预算与统一终审交付说明

日期：2026-10-29。实施基于现有工作树，沿用 Worker、POC SDK、SQLite 执行账本、验证门禁和不可变报告。自动验收只使用模拟模型、临时数据库和被拦截的浏览器 API。

## 1. 本次修复的闭塞

运行 `d3b17e8c…` 的问题不是全局请求、时间或上下文都用完，而是源码规划、逐项 retain、动态复核及最终处置共同占用了旧 Planner 回合容量。重复给候选执行 retain，以及把 Worker 后续建议直接当作审计义务，使这个容量更快耗尽。

新政策为 `task_spec.orchestration_policy=host-queue-v1`。`round_no/revision` 仍记录执行历史，但 `max_planner_rounds` 不再限制新政策；接口同时返回 `round_limit_applies=false`、`effective_round_limit=null`。旧记录缺少字段按 `rounds-v1` 解释，不回填、不切换、不追加调用。

## 2. 创建、复制与实验兼容

| 模式 | 整次模型请求 | 整次工具调用 | 活跃秒数 | 默认调度 |
|---|---:|---:|---:|---|
| 新普通全量审计 | 512 | 4096 | 3600 | host-queue-v1 / discovery_first / batch-v1 |
| 快速目标审计 | 256 | 2048 | 1800 | rounds-v1，保留原目标收束行为 |
| 新 Prompt 实验 | 保留实验安全上限 | 保留实验安全上限 | 每试次 720 | host-queue-v1，POC 关闭 |

`POST /api/runs` 按模式补齐未提供的预算分量，显式提供的值优先。配置接口增加 `run_budget_limits.profiles`，前端切换模式时同步显示和提交相应预算；用户已改的预算不因切换模式被覆盖。

复制历史任务保留冻结的调度政策、总预算、POC 模式和显式阶段配额。高级设置中的“使用当前默认配置”才切换到新默认值。复制不携带旧消耗。暂停、继续保留政策、配额、计数与审查记录。

新实验 manifest 显式冻结 `orchestration_policy`、`workflow_policy`、`review_policy`，继续保存宿主代码哈希和 AgentPolicy。旧 manifest 缺少调度字段时使用旧政策，缺少工作流字段时仍为 legacy。720 秒审计、780 秒生命周期、7200 秒首次批次及补跑口径均保持；评分仍依据截止前通过校验的候选，不改成终审接受数。

## 3. 宿主调度与无进展保护

- 初次规划默认一次 JSON 提交，最多 6 项明确范围任务，最多两次输出纠错。只有模型明确指出缺少具体上下文时，才执行一次聚焦补查并重新发布；不默认消耗探索和确认请求。
- 现有协调器负责 ready 领取、依赖解锁、并发补位与阶段切换。队列耗尽、覆盖复核、方向采纳或可修复阻塞才需要 Planner。
- 连续两次面对相同业务事实未取得进展，转入后处理。检查点保存在既有 workflow JSON；日志、任务改名、重复读取和优先级改变不刷新进展。新增已读范围、有效根因事实、评分变化及方向正式结算可以刷新。
- 普通候选只进行宿主校验、精确重复处置和索引维护，不领取机械 retain 批次。存在冲突、非精确重复候选或必做方向待判读时才整合；正常派工不被 pending integration 锁住。两次失败后批次 deferred，同版本不反复重试，义务保留至终审。

## 4. 必做方向与后续建议

新 Worker 的 `remaining_work` 产生稳定 ID 的 advisory，路径在当前任务内也不自动升级。Planner 通过具体任务的 `direction_ids` 或 assign 更新明确采纳后才变为 required；未知文件名保留诊断并拒绝直接升级。

Worker 不能降级已分派方向。required resolve 必须对应同一方向 ID、同一分配任务的 supported/no_evidence 结果、具体判读与真实读取记录，再由 Planner 明确结算。`completed`、读取过同文件或路径相交都不是自动结算理由。

摘要的 `unsettled_total` 在新政策下仅统计必做未决项，并另外提供 `required_total`、`advisory_total`。报告从冻结任务 JSON 完整提取建议，单列“后续建议”；建议不阻止收束。旧缺字段方向仍为 required。

## 5. 同一账本中的预算预留

`refresh_review_reserve` 和实际领取共用 `review_batches_pending` 打包器。待审结论和必须判读方向按 UTF-8 字节分批，每批最多 8 项、32 KiB；源码、完整观测和作业引用都会占容量，因此 B 不等于简单的数量除以 8。

设 B 为实际待审批次数，W 为运行中 Worker 加上本次拟启动 Worker 数：

```text
剩余审查请求预留 = 3B + 6W
停止新增上游工作的时间阈值 = 60 × (B + 2W + 1) 秒
```

自动分配从未消费 discovery、再从 POC 等量划入 review；剩余审查量下降时，上游阶段可以收回多余预留。`limits` 总和始终等于全局请求上限，各段不低于已消费数；所有角色仍使用原 `run_execution_state` 和 `workflow.used`，没有第二本成本账。

静态阶段停止后，可将自动分配的 discovery 未用余额转入 POC，覆盖不足及原停止原因照常保留。显式阶段配额为固定分配，不自动借额或扩额，前端即使填回与自动比例相同的数值也按用户固定选择提交。

时间阈值仅决定是否启动新 Worker / POC，不是新的执行硬截止。已准入请求仍受原单请求、Agent、全局及实验生命周期截止约束。原全局 watchdog 是整次硬截止；暂停不刷新额度，重启不重放实验。停止原因区分 `final_review_reserved`、阶段额度耗尽和全局预算耗尽。

## 6. 统一终审与原子门禁

取消新政策“每两条 POC 强制动态复核”的交替。POC 仍按当前规范实体版本、优先级、持久认领和剩余额度执行；每条开始前重算终审预留，不重复执行同版本。

final 输入提供当前结论、评分、来源版本、源码原文、正常／攻击观测、验证 ID、证据引用及作业记录。单次 PlannerDecision 可同时提交 `verification_reviews` 和逐项 `review_decisions`：

- 静态证据充分可 accept，动态状态保持原值。
- 尚未正式复核的 verified 若要 accept，必须在同次提交精确 finding/revision/verification ID 的 confirmed，并有完整正常与攻击观测。
- 冲突、反证、错误版本、未知验证及缺失观测拒绝接受；超长到不能完整装入单项的输入显式标为省略，只能 needs_evidence，不以摘要补造确认。
- 两类处置在同一个现有事务中校验、写入；任一非法项或写入异常均回滚。终审不派源码任务，不启动 POC。
- `review-facts-v2` 指纹包含结论、评分、证据、来源版本、验证及观测，排除复核输出和派生判断；提交 confirmed 不让自己立即过期。事实确有变化仍拒绝旧版本。
- 终审撤回或判重按规范实体覆盖本运行的相关来源记录，原文、证据和验证历史全部保留，并记录处置事件；避免旧版本重新浮起造成重复审查。

没有足够预算、取消或异常时，不追加模型总结。宿主生成阶段报告，待补证和未决义务明确保留；不补造 accept 或 verified。

## 7. 报告、前端与兼容

运行主界面显示阶段、结算任务、必做未决、建议、待验证及待终审项。回合序号保留在执行历史，不展示新政策的“当前/24”。阶段配额展示自动／固定分配、实际用量、预计批次数和当前请求／时间预留。

终态保存既有不可变事实包和宿主读取的源码及附件字节。页面 `/final-review`、JSON、Markdown、ZIP 使用同一事实包；后续修改发现不改变已冻结报告。报告区分静态终审接受与动态已验证，展示完整建议和真实补证动作。旧无批次报告继续使用旧复核口径，不能冒充新终审。

未修改历史运行、官方真值、评分锚点、原测试 JSON/ZIP 或实验成绩。本次不会把提高预算后的检出量变化直接归因于调度改进。

定向用例位于 `backend/tests/test_host_queue.py`，另回归受影响的创建、方向、暂停恢复、工作流、实验时限、POC 配额、验证复核及报告测试。

- advisory 不阻止收束；显式采纳后，Worker 不得降级；有同 ID 取证和 Planner 判读才能结算。
- 整合待审或 deferred 不阻塞无关任务；同版本不机械重复领取。

- 浏览器检查深浅主题及 1440 / 1024 / 768 / 390px，另检查冻结报告四种宽度、日志、JSON / ZIP 下载、历史复制与显式重置。
