## 1. 先保留验证及覆盖复核机会，再判断阻塞停滞

Worker 波次结束、没有 ready/running 任务时，协调器按以下顺序处理：

1. 对当前仍主张的源码结论执行该运行允许的 POC 验证。
2. 对未读覆盖路径请求 Planner 复核，派发业务方向或逐文件记录 skip 理由。
3. 只有覆盖复核已处理完毕或到达其有界上限后，才检查真实 blocked 任务是否持续没有进展。
4. 仍未结算的业务方向继续阻止全量审计宣告完成。

`deferred` 任务不会压住其它文件的覆盖复核。Worker 尝试额度耗尽后，仍可使用剩余
Planner 和全局预算记录跳过理由；这不提供新的 Worker 执行额度。
覆盖复核有自己的无进展上限，避免持续无效规划。

部署脚本、配置及测试夹具不会自动被跳过；Planner 必须引用冻结快照中的具体文件并提供理由。
文件 skip 也不会自动把一个业务任务的 `remaining_work` 标为完成。

## 2. 原子缩小并重开 blocked 方向

沿用现有 PlannerDecision 的字段，同一回合可以同时提交：

```json
{
  "tasks": [{
    "task_key": "sql-injection-dataflow",
    "title": "补查剩余查询参数",
    "objective": "只处理前次尚未结算的数据流",
    "acceptance_criteria": "保存有已读源码依据的结论或排查记录",
    "rationale_summary": "缩小原任务，避免重复已保存的工作",
    "source_refs": [{"path": "实际快照中的完整文件路径", "start_line": 2, "end_line": 3}],
    "dependencies": []
  }],
  "updates": [{
    "task_key": "sql-injection-dataflow",
    "action": "reopen",
    "rationale_summary": "缩小读取窗口，继续前次未结算的方向"
  }]
}
```

示例中的文件路径及 dependencies 必须替换为真实快照路径和原任务依赖。
宿主在同一事务内更新 blocked 任务的定义并计一次重开。任务 ID、原依赖、历史尝试、旧结论及旧计划快照保留。
不能通过换定义删除依赖前提或绕过任务/运行重开次数上限。

只重复使用 blocked 的任务键仍会被拒绝；必须显式提交 reopen。
运行中的任务和其它结算状态不能用同键提案改写定义；按旧定义补查仍可只提交原有 reopen。
Store 在写锁内重复检查状态和额度，防止陈旧决策或直接调用绕过模型侧校验。

## 3. 运行内二档宿主去重

精确重复第一档保留。二档改为：

- 规范漏洞类型、主定位路径、主定位行完全相同。
- 危险操作的 `sink_similarity >= 0.6`。
- 满足阈值的开放候选恰好一条；多条满足时保留歧义，不按最高分强行选择。

阈值及唯一候选步骤与项目账本的 `pick_merge_candidate` 共用。运行内二档不使用账本的
证据覆盖回退来合并不同操作，也不要求输入来源或适用前提的自然语言描述逐字相等。
未知分类、缺失定位及明显不同的 sink 不自动合并。

宿主只把新报告标为 `duplicate`，记录原报告 ID、判重层级及相似度；正文、证据、POC、CVSS 和来源仍可追溯。
评分器继续读取真实处置后的当前主张，不增加隐藏的评分去重步骤，不更改匹配规则。

对原 46 条开放发现进行只读、按创建顺序的预演，可按新规则标记 3 条重复，保留 43 条主张。
剩余仍有 10 组同坐标主张；描述未达到阈值的不能假定为相同漏洞，需要 Planner 进一步复核。
该预演没有写回数据库，也不代表真实 TP、F1 或检出能力已经改善。

## 4. POC 不再依赖静态审计成功收束

协调器在空闲前沿及统一终态入口调用同一验证门禁，因此 Planner 直接请求 `inconclusive` 也不会跳过已有结论。
验证继续使用原运行预算、执行代次及按结论版本持久化的作业认领，不重复提交同一实验。
显式 `mode=off` 优先于服务器 enabled 配置；暂停、取消和截止后不启动新验证。

验证失败、环境不可用及 `inconclusive` 不会变成 `verified`。
POC 已执行也不能消除业务阻塞；`required` 仍要求有效动态证据，已验证结论仍须原有 Planner 复核。
