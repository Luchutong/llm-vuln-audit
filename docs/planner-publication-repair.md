本次没有发现结果的直接原因是**任务派发之前的决策发布失败**。这次记录不能用来判断靶场没有漏洞，
也不能用来评估 Worker 的挖掘能力。运行没有用完原定的 30 分钟，而是触及无效输出的纠错上限后结束。

原发布阶段要求模型生成 Python 字典并调用 `final_answer(...)`。两轮共六次发布均未成功：
第一轮分别出现空正文且达到 8192 token 上限、Python 语法错误、动作边界未闭合；第二轮出现三次未闭合动作，

四条响应以 `length` 结束，其中两条消耗 8192 token 却没有正文。

这些现象表明，发布阶段承担了不必要的动作封装和 Python 执行要求，同时缺少足够简单的小批任务发布路径。
仅延长时间或扩大输出额度不能保证决策可落库。

## 修改后的执行方式

探索和少量确认继续使用 CodeAgent，只读工具、源码读取账本和证据隔离规则保留。
探索阶段最多使用 `AgentPolicy.planner_explore_responses` 指定的请求数，默认 3 次；
同时仍受原有请求、工具和时间预算约束，且必须为最后发布及纠错保留额度。

最终 `planner_publish` 阶段改为宿主控制的 JSON 发布：

1. 使用当前项目概览、态势及覆盖信息构造新的有界请求，不带入前序 CodeAgent 的整段动作历史。
2. 模型只返回一个符合 `PlannerDecision` 的 JSON 对象，不执行 Python，也不调用工具。
3. 该请求单独关闭 thinking；探索及其他角色原有的模型配置保持原样。
4. 宿主先解析 JSON，再执行现有决策类型、路径、依赖、任务状态、证据及复核校验。只有通过校验的决策才能进入任务前沿。
5. 格式、类型或业务校验失败时返回简明错误，让模型修正；默认最多两次纠错，即最多三次发布请求。

`planner_publication_tasks` 默认限制每次发布最多 2 个任务，约束对探索、确认及最终 JSON 发布统一生效。
提示提供一个完整、可校验的单任务示例，引导模型先交付一小批可执行方向，再由后续轮次扩展。
其余方向由后续 Planner 轮次继续处理，不把一个大而脆弱的决策当作全源码覆盖的前提。

探索或确认因为无进展、上下文上限、动作格式纠错耗尽而结束时，仍可以进入最终 JSON 发布。
它们已经消耗的请求和工具不会归零；最终发布和两次纠错也必须使用同一轮的剩余额度。
全局预算耗尽、用户取消及提供方错误仍按原有类别停止，不能通过切换阶段增加额度或掩盖终止原因。

本次不扩大 8192 token 输出上限，不调整已有运行预算，不降低源码证据、POC 及结论收束门禁，
也不改写历史运行的状态、发现或评分。

## 错误恢复与可观察性

最终发布记录结构化输出的解析及校验结果，模型响应保留实际 `finish_reason`、输出额度和 thinking 设置等诊断信息。
原始模型推理正文不写入持久日志；错误提示不直接复制整段失败响应。

前端日志分别标注空正文、输出额度耗尽、JSON 格式错误及宿主决策校验拒绝。
JSON 发布没有 Python 动作事件，错误统计仍按请求归并，并以成功提交或阶段成功结束作为恢复依据。

取消后关闭发布门禁，迟到响应不能提交决策或触发新的纠错请求。
连续三次无法提交有效 JSON 时明确记录无效输出，保留已消耗用量和失败草稿，不伪造任务或漏洞。
可恢复的发布失败可以在原额度内修正，无法恢复的失败仍如实结束。
