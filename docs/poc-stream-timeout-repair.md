# POC 模型流式超时修复

日期：2026-10-30。调查任务：`0ce53564276b58859f5a382095f482f4`。

## 观测与定位

该任务 12:34:27 开始，使用 `deepseek-flash`。调查时仍在执行，没有暂停、取消或重新提交它的任何作业。

首条 POC 的六次 `HTTP 200 / stream_timeout` 均出现在对应模型请求开始后约 61–63 秒；随后还有一次等待上游超时。SDK 实验阶段累计运行约 435 秒，结论阶段没有完成，记录为 `inconclusive / conclusion_error`。

网关原本将固定 60 秒同时作为请求及整个 SSE 响应的硬截止。即使中间一直有输出也不会延长窗口，导致较慢或较长的生成被截断。HTTP 200 仅代表已收到响应头，不能说明模型响应完整。既有日志没有保存流进度，不能再精确断言这些旧事件中每次是否仍有数据到达。

另外，旧网关会继续等待上游 HTTP 流关闭，即使已经收到 Anthropic `message_stop`；如果兼容端保持连接，也可能产生多余等待。本次一起修复，不能将它直接认定为上述历史事件的已证实原因。

## 修改

- 单请求默认总时限 180 秒，流空闲时限 120 秒，分别由 `POC_CLAUDE_REQUEST_SECONDS` 和 `POC_CLAUDE_STREAM_IDLE_SECONDS` 配置，允许范围 `(0, 600]`。连接建立最多 10 秒。
- 总时限仍从请求开始计算；空闲时限从最近一次收到数据开始计算。心跳或持续输出可避免空闲超时，但不能突破单请求总时限。
- 请求时限取配置值、当前能力所剩时间和审计剩余时间的最小值。SDK 能力 TTL 同时受当前实验／结论阶段截止限制，不侵占预留的结论窗口，也不提高审计总预算。
- 收到 `message_stop` 立即结束转发并关闭上游连接；支持分块及 CRLF。上游错误事件正常转发并结束，不再追加一个误导的超时。
- 若没有结束事件就遇到 EOF，记录 `stream_incomplete`，不视为完整生成。持续沉默、总时限、连接异常、输出过大分别归类。
- 无数据期间也检查上下文是否停止，撤销后停止读取，不等待 120 秒空闲时限。请求仍只准入一次；不添加网关重试，不重放 POC，不放松证据门禁。
- 错误诊断增加耗时、空闲时长、接收字节数、事件数、最后事件类型及配置时限；不保存正文或凭据。前端用中文展示原因，说明 HTTP 200 的含义，隐藏无意义的 `unknown` 占位。旧 `stream_timeout` 明确标注旧记录没有细分原因。
