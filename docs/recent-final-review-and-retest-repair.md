# 最近终审故障与复测继续任务修复

日期：2026-11-09。调查对象：`588ca76c3b0045e5b1769f32e52ebc40`。修复基于 `924378d`，不修改父运行的终态、验证、终审批次或冻结报告。

## 原运行为什么没有闭合

该运行于北京时间 18:40:18 开始，19:40:33 结束，最终为 `inconclusive / run_budget_exhausted(seconds)`。消耗 228/512 请求、298/4096 工具、3602 秒。原始发现 23 条，其中 11 条为重复记录，剩余 12 条规范结论全部待终审；9 条 verified、1 条 inconclusive、2 条 unverified。

终审约于 19:27:55 开始。事件 `75187`、`75246`、`75302`、`75325`、`75347`、`75369` 记录了六次回合失败，主要阻塞为：

1. **对照合同不够明确。** 模型反复仅填 `distinct_from`，缺少 `explicit-peers-v1` 要求的逐项 `comparison_assessments`，或者将判读写入不存在的 `relation_note`。错误只给出概括性要求，没有同时点明每个 item/peer 缺少的字段。原提示也仍强调只在总 `rationale` 中说明差异。
2. **关联候选被拆到不同批次。** catalog 同一位置有四条候选，字节打包先领取其中两条。主结论若想 accept，需要说明它与其他保留对照的差异；但这些对照很可能本就应判重，且不全在当前租约内，无法同时处置。不能靠机械填 distinct 将相同根因包装成不同漏洞。
3. **动态复核与静态处置混用。** 运行提交过与当前状态或版本不符的 `verification_reviews`。inconclusive/unverified 没有可确认的完整双侧结论，不能补造动态 confirmed；它们仍可进入独立静态审查。
4. **失败项过多占用时间。** 每轮已包含发布和纠正，同一冻结批次仍多次重问。首批消耗大部分预留时间，后续结论没有充分机会领取。

## 修复

- `agent.py`、`submission.py`：统一逐对照的 item_id/relation/rationale 合同，说明同根因保留主结论及 duplicate 的成套提交方式；标明对照是否在当前批次。动态复核只列当前批次 verified 的精确 finding/revision/verification 引用，未决实验明确省略动态确认。
- 审查请求只携带目标、当前冻结批次及必要事实，发布 schema 只列审查动作与其引用的定义，减少调度任务、目录导航等无关内容。实际发布仍使用完整模型和 Store 校验，没有放宽证据、版本、双侧观测或真实差异要求。
- `review_policy.py`、`review_store.py`：将候选对照及动态复核的错误按具体项一次列全，提供可修正的字段与引用。不自动填关系、选主结论或确认漏洞。
- `review_store.py`：对已冻结 `explicit-peers-v1` 的任务，能在预算内完整审查的关联组件保持同批，最多 8 项、128 KiB，且受冻结历史容量一半的约束；每项原有 32 KB 分页界限保持。超过边界仍分批，不取消容量保护；无关小项和旧版对照政策保持原打包方式。
- `worker.py`：宿主终审中相同失败连续两轮即拆分或延后该批，继续其他结论。不同错误仍允许有界纠正；未完成项仍计入终审缺口。

## 真实副本验证暴露的分页问题

第一轮隔离验证完成两批后，在第三批发现 `KeyError: 'payload.related_claims'`。该旁证字段由打包器按其他当前结论及源码生成；原分页读取端只重建 `_review_candidates()` 的基础字段，没有重建这份旁证。字段一旦被移出内联内容就无法读回，剩余源码/验证字段也被同一读取代码中的异常打断。

修复为共享确定性的 `_review_source_inputs()` 投影，用于打包以及该派生字段的分页读回。普通原始验证字段仍只读取自身，避免每页重复生成全量旁证。分页仍核对原字符数、SHA-256、实际已读区间、租约及当前版本；不能用空正文或跳过阅读绕过校验。

第一轮在明确该错误后停止，保留其消耗和失败记录：[分页修复前验证](validation/recent-final-review-before-pagination-fix-2026-11-09.json)。随后在新的数据库副本重验，模型仍为原运行的 deepseek-flash，新增上限为 64 请求、1024 工具、900 秒；只补终审，不提交 POC 或复位靶场。结果记录在 [修复后验证](validation/recent-final-review-live-2026-11-09.json)。

## 对已有记录和复测的适用方式

上述修改位于终审共同路径。普通新审计、`review` 仅补终审、`poc_review` 复测后终审，以及 `audit` 继续源码任务，均通过相同打包器、分页读取、发布提示和 Store 门禁。继续任务不复制父任务失败批次租约，会依据子任务的当前引用重新领取。

本次回归直接驱动真实协调器，验证了：子任务保留原 comparison policy；复测只执行所选项；成功验证不重跑；新验证与继承验证使用各自精确引用终审；同根因可在同一事务保留一个主结论；父冻结输入不变化；没有补成动态成功的静态接受仍保留未决状态。

父运行另有 `sqli-content-support-partner` 源码任务受阻，其 `content-lfi` 候选依赖未提供的源码事实。这个缺口不是终审格式故障：仅补终审或仅复测不会自动消除它，不能为了得到 completed 修改原结论或删除候选。终审完成与整个源码审计完成分别表达。

## 本次复测的宿主约束修复

针对仍在运行时大量报错、目前已暂停的复测继续任务 `f1f9fa946dc350c7a611d90e67b5b463`，本次进一步替换终审的读取与纠错协议。下面的规则替代上文原有的“模型最多两次读取请求、关联组件最多 8 项／128 KiB、按失败回合计数”等实现限制。

1. **引用与正文分离。** `reference_coordinates` 始终内联保存每个 peer 的规范 item ID、finding 别名、版本以及源码坐标。发布合同完整列出合法动作和字段层级，`comparison_candidates` 正文分页不会导致 peer 列表或判读示例消失。引用坐标仍不授予源码或分页已读凭据。
2. **宿主组装分页。** 宿主验证字段原文的 SHA-256 与长度，按 4096 字符处理尚未读取的区间并持久化游标；旧租约失效，精确相同对象版本与字段哈希的读取区间可复制到新租约。发布输入还原为有类型的完整事实，不再要求模型执行 Python 分页循环、拼接转义 JSON。分页不消耗模型读取请求，预算预留按剩余真实页数计算宿主读取工作。读完且完整输入与纠错合同都能放入上下文窗口后才开放 JSON 判决；无法容纳的关联组整体延后，保留未决，不拆开根因对照或截断事实。派生事实发生变化时立即作废旧租约，按当前哈希重新领取，旧字段游标不能冒用。
3. **阶段及对象合同。** 每个 schema 分支绑定当前 item ID、revision、peer ID 枚举与阶段合法动作，integration 没有 accept，动态复核仅在 final 顶层 `verification_reviews`。宿主补齐省略的当前引用，显式错误引用照常拒绝，不代填语义判决。新增 `LLM_STRUCTURED_OUTPUT=compatible|json_object|json_schema`；只有明确支持的连接才选择原生结构化输出，新运行冻结其能力，旧运行及其它保存档案保持兼容模式。
4. **持久化纠错额度。** SQLite 新增 `audit_review_allowances`，按 run／对象／事实版本记录总发布次数和错误类型。连续两次同类错误即延后该项，总发布最多三次；拆批、换回合、暂停恢复、进程重启及阶段切换均不重置。能定位到具体项的字段错误只记到该对象；无法归属的格式错误按当前批次计入。已耗尽项留在未完成报告中，其它健康项继续审查。历史事件不被回写为新协议计数，旧运行的全局已消耗预算继续保留；显式创建新的继续任务才拥有新任务自己的额度。
5. **代码动作执行前约束。** 默认单动作最多 8192 字节、80 行、768 个 AST 节点、8 次工具调用，均先检查再执行；循环的实际工具次数另受运行时上限控制。直接或简单赋值后将文本工具结果交给 `json.loads` 会在任何前置工具执行前被拒绝。修复依赖库超时后仍等待线程退出的问题，并使超时动作持有的工具回调失效，不能借用下一动作的额度或工具表。

普通审计、仅补终审、复测后终审和继续源码审计共用以上 Store、Planner 发布和执行器路径。数据库变更为新增表；不修改已有发现、验证观测或冻结报告。当前生产任务保持暂停，未重启服务、未触发真实 POC，也没有把隔离验证的判决写回用户记录。
