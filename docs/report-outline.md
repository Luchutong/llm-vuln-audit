# 审计报告与漏洞交付目录

当前阅读模板为 `delivery-report/v1`，冻结事实为 `final-review/v1`（历史）或 `final-review/v2`（新能力策略）。统计和完成性由宿主事实生成，正文重排版不会重新终审或改变历史评分。任意上传项目均不假定为 Lab30；其源代码不会由审计进程执行。

## 报告选择与格式

| 阅读视图 | Markdown 内容 | JSON 范围 | ZIP 主文档 |
| --- | --- | --- | --- |
| `audit` | 源码包、原始目标、完成性、六列清单、覆盖缺口、后续行动 | 全运行的派生交付文档 | `report.md` |
| `vulnerabilities` | 按接受、待审、存疑/排除分区的漏洞详单汇编 | 同一冻结运行全部规范结论 | `vulnerability-report.md` |
| `accepted` | 已获独立终审接受的漏洞详单，可在父任务仍有未决项时独立交付 | 仅已接受的引用闭包，父任务统计单列 | `accepted-findings.md` |
| 单条规范结论 | 一条漏洞的证据、前提、复现、终审、CVSS、修复与复测 | 单条引用闭包，父运行统计仅在 `parent_summary` | `finding.md` |
| `archive` 或省略 view | 原始归档 Markdown | 原始归档 JSON | 原始归档 ZIP |

三种格式为 `markdown/json/zip`。旧接口省略 `view` 的字节和 ETag 保留；阅读版使用独立内容哈希。报告抽屉默认选择审计执行报告，仍可选已确认报告、包含待审的漏洞汇编或归档原件。运行结果卡在存在终审接受项时直接提供已确认漏洞报告下载。运行结束且拥有冻结输入/事实后才提供正式阅读版。

整次审计是否完成与部分漏洞能否交付分别判断。`accepted` 只选已获独立终审接受的冻结结论，不因动态状态为 verified 就将待审项自动升级；正文披露父任务的未决数量和整体完成状态。原历史处置和质量结论保持原样；同根因仍待判读时，不重新合并台账或声称这些编号都是不同根因。

## 审计执行报告

1. 开篇列源码包、原始目标、时间和历史重排版说明。
2. 结果与完成性：区分执行状态、目标关联、源码复核、冻结风险义务、动态要求、独立终审与交付材料。
3. 六列漏洞清单：稳定短编号、标题与主位置、CVSS 分值/严重程度、动态验证、独立终审、详单。完整向量进入详单。
4. 覆盖与未完成工作：应审文件、实际读取、读取或带理由跳过后的复核、方向与风险义务分别计数。跳过、受阻、未执行均不是安全结论。
5. 后续行动：补证、修复和复测材料缺口；缺少修复不撤销已成立漏洞。
6. 限制与追溯：冻结 input、facts、原始 output、renderer 和 template 哈希。

新任务将目标相关、必要辅助链、附带发现、相关性未定分别显示。附带发现保留台账；辅助链不独立支撑目标达成。历史没有记录目标相关性的结论不重新归类。

## 单漏洞详单（汇编复用此模板）

1. 标题、稳定编号、结论/评分修订、证据快照与两类状态。
2. 影响与受影响位置：只描述源码或实际验证已支持的影响。
3. 利用前提：攻击前登录身份、资源属主、CSRF、业务状态与必要配置。
4. 根因与源码证据：输入、转换/防护、持久化/读回、危险操作；每段绑定实际快照行号。静态导航不算证据。
5. 复现与实际验证：脚本、正常/攻击输入及**预期**判别；另列实际作业观测、身份、状态变化、继承来源和实验合同。HTTP 200 或退出码 0 不表示漏洞成立。
6. 终审结论与限制：实际独立终审批次理由；动态观测的独立复核另列。
7. CVSS 3.1：完整向量及已冻结指标依据，不推测未记录指标。
8. 修复建议与复测：保留完整段落，缺失材料明确待补充，不在导出时请求模型编造。
9. 来源与附件：运行、规范身份、结论/评分版本、源码/观测/脚本引用及哈希。

没有动态记录时标为待执行材料；未验证不等于排除。存疑与排除单列；零结论只能称“本次未形成可交付漏洞结论”，不能称项目安全。

## 冻结、证据与质量

阅读版只读取父运行已保存的冻结事实及 input。历史片段不完整时显示缺口，不补读当前源码。单条 JSON/ZIP 不携带其他漏洞正文、父运行全量事实或无关附件；规范 ID 的归属以父运行冻结列表为准，不能直接查最新台账。

全量 ZIP 包含主文档、汇编、逐条 Markdown、原冻结 `final-review.json`、`manifest.json`、独立 `render-quality.json` 和引用附件。单条包改用 `finding-facts.json`，已确认包改用 `accepted-facts.json`；两类筛选包都不携带父任务完整事实或范围外漏洞正文。压缩包按固定时间/顺序生成；manifest 记录主文档、编号映射、来源和产物哈希及缺失附件。

历史原始 `quality_result` 保留；新布局校验独立检查范围、计数、引用归属、编号、章节、锚点、围栏和表格。认证头、Cookie、令牌查询参数和 API 凭据在 Markdown 呈现中脱敏；JSON/原始附件保留冻结事实，其来源和哈希单独标注。

派生导出缓存采用加法表，按来源哈希、模板、视图、规范身份和格式区分；删除运行同事务清理，迟到渲染不得恢复被删除记录。不能删除不可变触发器或改写原冻结报告。

## 兼容与实际限制

- 新任务 `poc_mode=off` 时不要求动态通过数量；`auto` 为可选；`required` 仍要求至少一条目标相关、源码/版本/目标兼容的验证，现有独立复核保持。
- 新能力策略只在新建任务冻结；旧运行不回算完成性，继续任务须重新适配当前目标关联门禁。
- 深度风险义务为可选 `bounded-v1`：从 PHP 显式操作调用信号生成，最多 256 项。未解析动态关系、输出语句和其他语言的完整风险图仍需规划与人工复核，不宣称穷尽所有风险。
- 当前 runner 没有崩溃后的“恰好执行一次”协议；沿用现有占位与未知结果处理。
- 真实 API 模块试验不等同于全量真值召回评测，失败试验与成本应保留。
