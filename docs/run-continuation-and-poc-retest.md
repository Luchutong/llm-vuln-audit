### 直接阻塞

1. LFI 的 SDK 实验阶段触及阶段时间边界，随后结论阶段等到尝试截止才取消读取任务，未给原生 CLI 清理留下时间，记录了 `sdk_cleanup_timeout`。该尝试保存 5 个作业，不能把没有最终结论解释成没有实验事实。
2. 终审领取的小批中，仅一个对象需要读取 `payload.verification_job_facts`。模型把这个字段套到另两个没有该字段的对象上，触发参数拒绝；另一轮逐页读取又占用了全部三次响应。宿主随后仍进入独立发布阶段，但已没有本轮响应可用，连续两次失败后停止，留下 13 项未审。日志中的“模型请求预算已用尽”指**本轮三次响应**，不是全局 528 次上限。
3. 原发布阶段会重新构造提示，只保留字段清单；读取阶段拿到的正文没有进入新的结构化发布请求。仅延长全局预算不能修复这个事实断点。
4. Cookie 授权绕过的首次结论引用了正常侧作业，却漏把该作业写入冗余的 `jobs` 支撑集合，门禁正确拒绝；后一次修正已经通过。这里不是 HTTP 门禁失效，不放宽真实性检查。

## 修复

### 终审读取与发布

- 在原每批至多三次响应内，读取／代码动作最多使用两次，始终给结构化 JSON 发布留下至少一次。
- 宿主按 item、字段和偏移保存本回合实际返回的页面。进入新的结构化发布请求时携带这些原文，不依赖模型自行摘要或复制。宿主原有读取区间、精确版本、暂停及证据完整性校验继续生效。
- 提示明确只读取**各对象自己的** `paged_fields`，没有分页字段的对象无需读取；不假定解释器预置 `batch` 变量。必读事实未读完仍保留待审，不能用假处置绕过。

### POC

- 结论阶段输出的截止时间提前，给 CLI 清理保留最多 25 秒、且不超过单项尝试时间的 10%；清理与模型等待仍全部位于原单项和全局硬截止之内。
- 结论阶段清理失败的实际原因保留为 `sdk_cleanup_timeout`，不再统一降为模糊的 `runtime_unavailable`。
- 两侧 `evidence_ref_id` 解析成当前上下文中有效的宿主引用后，宿主补齐其对应的 `jobs` 集合。未知引用、显式失败作业、身份不符、伪造片段及纯 HTTP XSS 仍被原门禁拒绝；超过支撑作业上限也明确拒绝。
- 拒绝事件同时保存模型原提交的 `job_ids` 和补齐后的 `resolved_job_ids`。

## 用户操作

打开已结束的宿主队列审计，在结果区域选择 **“复测与继续审计”**。可选三种范围：

| 范围 | 执行内容 |
|---|---|
| 复测未决 POC，再完成终审 | 选择一个或多个当前未决项，开启新验证上下文，随后统一终审 |
| 仅补终审，不执行新 POC | 复用已保存的源码、原始作业及验证观测，补齐终审批次 |
| 继续源码审计、验证与终审 | 保留原任务与读取历史，对可继续的阻塞任务补充尝试，再完成验证与终审 |

原运行和冻结报告不变，系统创建一个关联的继续任务。任务创建后进入现有 Worker 队列，新增消耗独立统计；原运行页面的复测窗口可查看关联继续任务，子任务可返回原审计。没有创建第二套 Agent 或成本账本。

默认新增预算为 **256 次请求、2048 次工具、1800 秒**；单项 POC 默认 **600 秒、12 个作业、SDK 实验 60 次请求＋结论 3 次请求**。均可在窗口中调整：整次请求最高 4096、工具最高 32768、整次时长最高 14400 秒，单项时长最高 3600 秒、作业最高 32 个、SDK 实验最高 512 次、结论 3–16 次。

单项配置仍受阶段、整次剩余请求与时间限制。选择全部 13 项不代表 1800 秒内一定完成；需要更长窗口时由用户明确提高新增预算。原运行未使用的余额不偷偷转移，新增任务采用自动阶段分配及统一终审预留。原运行的固定分配保持原样。

### 继承边界

- 同一 ZIP、原源码范围、模型档案和 Worker 策略保持可追溯；模型档案及目标环境需要仍然可用。
- 发现、验证和任务获得新本地 ID，原始作业／上下文 ID 作为历史事实保留。历史验证带有 `continuation_source`；源码读取及必做方向继续来自持久记录，不因创建继续任务而被标为已完成。
- 只重绑定宿主任务引用，不改写原始观测、HTTP／脚本输出、源码引用、脚本或 CVSS 来源；即使正文恰好包含旧 ID 也保持原文。报告逐条标注继承验证的原运行和原验证 ID。
- 不复制已消费预算、活跃 claim、SDK 能力或旧作业所有权。追加预算和所选对象冻结后，暂停／继续不会重置它们。
- 原已继承的结论版本独立冻结；暂停前新增或修订的结论恢复后仍会进入验证，不能误当成原来的已完成版本跳过。
- 默认只复测未验证、未决、过期或正式复核存疑的当前结论。已验证且无争议的项不重复执行，撤回及重复记录不能被选中。
- 未受影响的已接受终审可沿用；复测所选项及其关联候选重新进入终审。同一台账出现新版本后，旧版本处置按原有事实指纹规则失效。
- 复用的源码读取记录支持覆盖统计，其历史费用不重复计作本次消耗；报告分别标注原运行用量和本次新增用量。
- 复测使用新上下文，不自动重放原副作用作业。未确认结束的旧作业仍受到 runner 租约保护，不提供强制绕过占用的入口。
- 单独提高预算不能解决未知环境前提。仍沿用原运行的人工／自动重置政策，不宣称新 Cookie 会话恢复了数据库状态。
- 所选或新增 POC 仍未形成确定结论时，即使静态终审接受，也保留 `inconclusive` 和 `poc_unresolved`，不把静态接受补造成动态验证。

## 接口

- `GET /api/runs/{run_id}/continuation`：只读返回支持情况、当前规范结论、可复测项、原待审数量、已有继续任务及默认配置。
- `POST /api/runs/{run_id}/continuation`：显式创建并排队，返回 201 和新的运行对象。

示例：只补终审。

```json
{
  "request_id": "review-after-timeout-20261030",
  "mode": "review",
  "finding_ids": [],
  "run_limits": {"responses": 128, "tools": 2048, "seconds": 1800},
  "poc": {"max_seconds": 600, "max_jobs": 12, "execute_requests": 60, "conclude_requests": 3}
}
```

`finding_ids` 为当前运行发现 ID，不是台账 ID。省略或传 null 选择全部可复测项，空数组明确表示不选。`review` 模式不执行 POC；`poc_review` 模式没有所选项则拒绝。预算、类型和范围非法返回 422 或 409；不存在返回 404。

同一 `request_id` 和参数重试返回同一任务，不重复开立预算；换参数复用同一 ID 拒绝。已有直接关联的 pending／running／paused 继续任务时，不再创建另一个。任务及全部继承数据在同一 SQLite 事务提交，失败全部回滚。
